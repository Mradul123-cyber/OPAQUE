Auto-backup Stage 2 (2026-09-21): automatic scheduling is acknowledged by WorkManager before Flutter reports enabled. Identical configuration does not replace the scheduled job; explicit frequency/time/credential changes do. The backup screen offers a time picker and reads next-run time, progress, cancellation state, last successful automatic backup and plain-language failure messages from native state. Existing configurations without a stored time retain 19:59; new configurations default to 00:30. Monthly means a 30-day interval. WorkManager timing is approximate and can shift with OS delays; this is not an exact alarm.

Native cancellation is bound to an individual run and checked during message export, encryption/write boundaries and publication. Cancelling one run retains the recurring schedule; disabling auto-backup invalidates its generation and cancels scheduled work. Native/manual notifications use separate IDs. Temporary I/O/lock failures retry with exponential backoff, at most three attempts per periodic run; permission/configuration failures disable the schedule with a plain-language explanation. Android 8/9 uses shared Download/Zarq_Backups with runtime storage permission, including list/read/rename/delete support. Pending/partial files are excluded from the backup list. Debug triggers use the same worker pipeline. Stage 2 Dart analysis: no errors, existing diagnostics remain. compileDebugKotlin passed after retrying a resource-exhausted/contended Gradle build with one worker and a smaller heap. No runtime tests or APK installation.

Auto-backup Stage 3 implementation (2026-09-21): native automatic backups stream SQLCipher message rows through a JSON writer and AES-GCM into an encrypted private temporary file, then copy it in 64 KiB chunks. The existing 2.1 archive schema and salt/nonce/ciphertext/tag layout remain unchanged. No plaintext temporary archive is written. Per-conversation metadata and Signal recovery state remain in memory; manual media backups and restore still use their existing memory paths.

After publication, encrypted file length and SHA-256 are compared against the completed encrypted source. A per-account ledger records exact URI, name, size, digest and creation time. Retention re-verifies recorded files and keeps the newest two valid recorded automatic backups per account. Pruning runs only after a new verified backup succeeds. Manual files, other accounts, pre-ledger backups, renamed files and unverified/corrupt files are not deleted. Failed cleanup or an unavailable ledger leaves backups intact for a later attempt. Interrupted private encrypted temporary files are cleaned on the next serialized run. Verification here means byte-for-byte publication integrity, not proof of successful end-to-end restore; Stage 4 still requires device recovery, interruption, Android 8/9 permission and retention checks.
